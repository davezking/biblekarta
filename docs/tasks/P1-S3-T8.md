## Why this model / review tier
- **Model:** config and docs, plus one CI check.
- **Review:** `opus`. This is the FR-29 gate: it decides whether content can go live without a second person.

## Context
- The Phase 1 review found that `CODEOWNERS` still had `@<OWNER>`/`@<REVIEWER>` (GitHub ignores them), and that the `main` ruleset wasn't active: eight PRs merged into `main` with no approval.
- The ruleset JSON in `docs/repo-rules.md` used `required_approving_review_count: 1`. That contradicts architecture §6 ("your own code PRs … merge after CI").
- **The owner (`@davezking`) is also the content reviewer.** GitHub never counts an author's own review, so with one code owner:
  - an editor's content PR still needs a second person: the owner approves it;
  - a PR the owner opens on a code-owned path (`scripture.lock`, `.github/`, …) can't be approved by anyone else.

## Do this
1. **`CODEOWNERS`:** replace both placeholders with `@davezking`.
2. **`docs/repo-rules.md`:** split `main` into two rulesets:
   - **`main-checks`:** PR required, `web` and `tools` required, no force push, no deletion. **No bypass.**
   - **`main-review`:** PR required with `require_code_owner_review: true` and `required_approving_review_count: 0`. The repository admin role may bypass it **only through a pull request** (`bypass_mode: "pull_request"`), so the owner can merge their own PRs on code-owned paths after CI. Editors (non-admins) can't bypass: their content PRs need the owner's approval.
   - Explain the one-reviewer trade-off: the owner's own content edits get no second person. Add a second code owner when one exists.
3. **`ci.yml`, `tools` job:** fail if `.github/CODEOWNERS` contains `<OWNER>` or `<REVIEWER>`.
4. **Owner (manual, documented):** delete any old `main` ruleset, run the two `gh api` commands, and enable secret scanning and Dependabot alerts.

## Acceptance criteria
- `CODEOWNERS` has no placeholders, and the CI check fails on one.
- A PR from a non-admin collaborator that touches `content/` can't merge until the owner approves.
- A PR the owner opens that touches only `src/` merges after `web` and `tools`, with no approval.
- No PR merges with `web` or `tools` red, the owner's included.

## Tests to write or update
- The CI placeholder check (shown failing on a branch that still has a placeholder).

## How to test manually
1. As a collaborator without admin rights, open a PR adding `content/sources/test.json` → it shows "Review required", and the merge button stays blocked.
2. Approve it as the owner → it becomes mergeable. Close it without merging.
