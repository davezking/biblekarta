## Why this model / review tier
- **Model:** an ambiguous mapping problem whose result decides the numbering of every reference in the app.
- **Review:** `opus`. A wrong map silently shifts verses everywhere.

## Context
The HTML forces **KJV numbering**. The scan has its own numbering, and every reference in the app uses the scan's. Known cases:
- **Job 40:25–32** are merged into 40:24 (inline numbers like `25፤`).
- **Ps 14:7** contains `[8]`, `[9]`, `[10]`.
- **Song 7:13** contains `[14]`.

There are likely more differences (e.g. Psalm superscriptions, chapter boundaries). Proofreaders confirm the scan's numbering in the workbook's "Versification" sheet. Input: `work/raw/` (HTML numbering).

## Do this
1. **The map format** in `scripture/versification.json` (produced at finalize; this task defines and validates it): a list of `{html: "job.40.24", scan: ["job.40.24", "job.40.25", …, "job.40.32"], kind: "split"|"merge"|"renumber"|"shift", note}`. Add a pure `apply_map(ref_html) → [ref_scan]` and `invert_map(ref_scan) → ref_html`.
2. **`versify_core.find_candidates(raw)`** detects:
   1. inline verse numbers inside a verse (`\d+፤` or `[\d+]`) → `split` candidates, with the proposed scan numbers
   2. chapters whose HTML verse count differs from a scan count known in `tools/bk/data/known_versification.csv` (start it with the three known cases; the proofreaders' confirmations get added there)
   3. a list of the chapters where Ethiopic/LXX-tradition printings commonly differ from the KJV (e.g. Psalms with superscriptions, Joel 2–3, Mal 3–4). Mark these `needs_scan_check`, not as a mapping.
3. **`bk versify candidates`** writes `work/versification-candidates.json`. The workbook exporter (P1-S2-T6) turns it into a sheet with one row per affected chapter: HTML count, proposed scan count, kind, and blank yellow columns for "Scan count", "Confirmed by" and "Reviewer".
4. **`bk versify build --from-workbook <xlsx>`:** turn the confirmed rows into map entries, refusing unconfirmed or unreviewed rows.
5. **Do not guess mappings** for the `needs_scan_check` chapters. They stay unmapped until confirmed. Finalize (P1-S3-T4) refuses books with unconfirmed chapters.

## Acceptance criteria
- On the real raw data, the candidates include Job 40:24 (split into 9), Ps 14:7 (split into 4) and Song 7:13 (split into 2).
- `apply_map` and `invert_map` round-trip for every mapped reference.
- No mapping is produced without a workbook confirmation, except the fully determined `split` cases, which still require confirmation of the scan count.

## Tests to write or update
- `test_versify.py`: detecting inline numbers in both styles; the map round-trip; refusing unconfirmed rows; the three known cases from fixtures.

## How to test manually
1. Run `uv run --project tools bk versify candidates` → it lists Job 40, Ps 14 and Song 7 as splits, plus the chapters needing a scan check.
2. Open `work/versification-candidates.json` → each row has the HTML count and the proposed scan count.
